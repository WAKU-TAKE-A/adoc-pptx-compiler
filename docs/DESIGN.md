# AsciiDoc → pptx コンパイラ 設計検討書

- 日付: 2026-11-11（初版の設計検討）
- 状態: 実装済み。本書は検討時の設計に、v0.9.3.0 時点の実装状況を反映した
  「設計＋実装記録」として維持する。各節の「実装状況」が現行の仕様である。
- 前提の議論と実測: `NOTES_md-pptx-injector.md`、試作: `adoc_demo/`（adoc2pptx.py、113行）

## 1. 目的と位置づけ

AsciiDoc で書かれた原稿を正本とし、納品時にだけ編集可能な .pptx へコンパイルする道具を設計する。

- 想定ユーザー: AsciiDoc で資料を書き、asciidoctor-pdf で PDF を出している人（第一ユーザーは開発者本人）。納品先に「パワポでちょうだい」と言われる場面が動機。
- これは md-pptx-injector の「流し込み」とは別系統の変換である。流し込みはテンプレート pptx のレイアウト／プレースホルダーを正とし、こちらは原稿の意味構造を正としてスライドを描く。
- 実装の置き場は、md-pptx-injector とは別系統の新しい道具として独立させる（2026-11-11 決定、詳細は §11）。

## 2. 確定した前提（議論より）

1. 最終出力は .pptx で変わらない。
2. 出力 pptx は自己完結でなければならない: 内容は通常シェイプ内の実テキスト・実オブジェクトとして入り、書式はシェイプ／run に明示する。マスター／レイアウト／テーマに必須情報を置かない（どの環境で開いても直接編集できるため）。
3. ユーザーが持つのは原稿テキストと記事の素材（画像等）だけ。背景などのデザインはツール側が持ち、素材ファイルの用意を求めない。
4. デザインの合意は「見本デッキの絵を見る」、内容の合意は「原稿を読む」の2点。道具側の追加成果物（中間表現、検証レポート）は派生物として自動生成し、人の負担にしない。
5. pptx はコンパイル成果物。再生成で戻せるが、直接編集された pptx を黙って上書きしない運用にする。

## 3. 全体構成

```
原稿.adoc (+ 素材)
  │  (1) フロントエンド: Asciidoctor を外部コマンドで実行
  ▼
DocBook XML（中間表現ファイルとして保存可能）
  │  (2) 正規化: DocBook 4.5 / 5 の差異を吸収した内部モデルへ変換
  ▼
内部モデル（文書ツリー）
  │  (3) 写像: 文書 → スライド列（写像規則 §5）
  │  (4) レイアウト: テキスト計測によるページ割り（§6）
  ▼
描画: python-pptx で通常シェイプを描く
  │
  ▼
出力.pptx ＋ 検証レポート（はみ出し・未対応要素・欠落素材）
```

- (1) はコマンドライン呼び出しとし、Asciidoctor が無い環境では明確なエラーにする。asciidoctor-pdf 利用者は追加の前提ゼロ。
- 中間表現をファイルに残せることで、解析側の問題か描画側の問題かを切り分けられる（§4 の実測がその実例）。
- バックエンドを持たない設計にする: 内部モデル以降は pptx 専用でよい。PDF は asciidoctor-pdf が既に担当している。

## 4. 中間表現: DocBook XML（実測済み）

取得方法は2経路とも DocBook を出すことを実測した（2026-11-11、adoc_demo/ir_check.adoc → ir_check.xml）:

| 経路 | 形式 | 備考 |
|---|---|---|
| 本命: Asciidoctor（Ruby）`-b docbook5` | DocBook 5（名前空間あり、link は xlink:href） | 構文カバーと拡張対応は最良。利用者は asciidoctor-pdf と同じ環境を保有 |
| 簡易: asciidoc-py（pip）`-b docbook` | DocBook 4.5（DTD、名前空間なし、ulink） | Ruby 不要。今回の実測はこちら |

実測で保持を確認した要素（asciidoc-py 経路）:

- section（入れ子）と title、段落（simpara）
- emphasis（太字は role="strong"、素の emphasis は斜体）、literal（コードスパン）、ulink＋本文（リンク）
- footnote（本文が要素として保持される）
- orderedlist / itemizedlist / listitem
- note（アドモニション）
- programlisting（language 属性つき、内容はそのまま）
- mediaobject / imagedata（fileref 属性で素材パス。ただし指定サイズは asciidoc-py では落ちた → 経路差として §11）

帰結: 内部モデルへの正規化層で「4.5 の ulink ↔ 5 の link」「名前空間の有無」等の差異を吸収すれば、描画側は経路に依存しない。

## 5. 写像規則（文書 → スライド）

原則: 写像は規約として明示し、原稿側の属性で上書きできる余地を残す。

実装状況（v0.9.3.0）: 下表のうち、文書タイトル／目次／節／小見出し／段落／
箇条書き／表／画像／コード／アドモニション／脚注は実装済み。book 形式では
chapter と preface も節として扱い、literallayout（`....`）は等幅ブロック、
variablelist（`用語:: 定義`）は太字の用語付き箇条書きになる。スライドの向きは
doctype で決まる（book=縦配置、それ以外=横配置、`--orientation` で上書き可）。
未実装: 水平線・改ページ `<<<` の明示区切り、節タイトルだけの章扉ページ、
`===` を属性で新ページにする上書き、表の列幅の内容量による調整。

| 文書要素 | スライド表現 |
|---|---|
| 文書タイトル＋著者・日付 | タイトルページ（1枚） |
| toc 指定時（または book） | 目次ページ（節・小見出しの一覧＋スライド番号） |
| `==`（レベル1節） | 内容ページの開始（タイトル帯に節タイトル） |
| `===`（レベル2節） | 既定は同一ページ内の小見出し。属性で「新ページ」に変更可 |
| 段落 | テキストブロック |
| 箇条書き（順序なし／あり、ネスト） | テキストボックス内の段落（レベルで字下げと記号） |
| 表 | ネイティブ表（ヘッダ行を強調、列幅は cols 属性→等分→内容量の順で決定） |
| 画像 | 実画像を配置（アスペクト維持、最大枠にフィット）、キャプションは下部のテキスト |
| コードリスティング | 等幅フォント＋背景色つきテキストボックス（背面に矩形） |
| アドモニション（NOTE 等） | 左帯つきの囲みブロック |
| 脚注 | そのページ下部の小さいテキストに集約（番号つき） |
| 水平線・改ページ `<<>>` | 明示的なページ区切りとして扱う |

- 節タイトルだけのページ（中身が小節のみ）は章扉ページにできる（オプション）。
- スライド番号とフッター（文書タイトル等）は生成時に全ページへ描く。

## 6. レイアウトエンジン（本丸）

スライドは固定サイズ（既定 13.333×7.5 inch）で、使える本文領域はデザイン定数から決まる。エンジンの仕事は「ブロック列を領域に詰め、溢れたら規則に従う」こと。

1. **計測**: 実フォントファイルで PIL により文字列幅を測り、折り返し行数とブロック高さを推定する。日本語は禁則を簡易に扱う（行頭禁則のみ）。python-pptx の fit_text は粗いので使わず、自前計測＋安全マージン（例: 高さ 5%）を持つ。計測に使うフォントが無い場合は平均文字幅ヒューリスティクスに落とし、レポートに記録する。
2. **ページ割り**: ブロック単位で次ページへ送る（ブロック内分割は箇条書きと段落のみ許可し、行単位で割る。表は行単位、大きすぎる場合は列幅調整→それでも無理なら警告して分割）。
3. **はみ出し方針**（CLI で選択、既定は a）:
   a. 継続ページを自動生成（タイトルに「（続き）」の印）— 実装済み
   b. フォント段階縮小（下限を決め、下限未満には縮めない）— 未実装
   c. はみ出しを許さず、その節を警告して止める — 実装済み（`--overflow error`）
4. **無言の欠落を禁止**: 入りきらなかった要素、未対応要素、見つからない素材は、必ず検証レポートにページ単位で出す。試作で起きた「スライド外に描いて消える」事故を仕様として封じる。

## 7. デザインの持ち方

- デザインはツール同梱の既定値＋テキストの設定ファイルで持つ: 色（タイトル帯、アクセント、本文、コード背景）、フォント（見出し／本文／等幅、東アジアフォント含む）、余白、タイトル帯の高さ、フッター文言、スライドサイズ。
- 実装状況: 形式は TOML に決定（`--design`）。キーの一覧と既定値は samples/design.toml が兼ねる（[colors] / [fonts] / [sizes] / [page]）。未知のキーはレポートの design_unknown_keys に記録する。運用調整用に、本文サイズ（`--body-size`）と本文1行の文字数（`--line-chars`、全角換算で本文の柱幅を決める）の2つのつまみを CLI にも出した（v0.9.3.0）。
- 背景や装飾は生成時に
...[truncated 3010 chars]図形として描き、マスター／レイアウトには置かない。
- デザイン変更の合意は見本デッキ（§10 の Phase 0 で生成する絵）で行う。

## 8. CLI の形（実装済み）

- 単一コマンド: `adoc-pptx-compiler src.adoc dst.pptx` を基本とする。
- オプション: `--design`（TOML）、`--frontend auto|asciidoctor|asciidoc-py`、`--overflow continue|error`、`--orientation auto|landscape|portrait`、`--toc auto|always|never`、`--body-size`、`--line-chars`、`--keep-ir`（中間表現 XML を残す）、`--report`（JSON レポート）、`--version`。
- 引数の流儀は md-pptx-injector と揃える（src / dst の位置引数、終了コード、ログ）。
- フロントエンドが無い場合は、導入方法を示すエラーメッセージで終了する（auto は asciidoctor → asciidoc-py の順に探す）。入力に DocBook XML を直接渡すこともできる。

## 9. 検証の仕組み（実装済み: pytest 17件）

- 単体テスト: 正規化（DocBook 4.5 / 5 の両形式）、写像、計測・ページ割り（既知の文字列量で割り切れること）。
- 結合テスト: サンプル原稿群（箇条書きのみ／表／画像／コード／脚注／長い節）から生成し、読み戻して「全テキストが pptx 内に存在する」「スライド外に置かれたシェイプが無い」「画像が実ファイルとして埋まっている」を機械チェックする。
- 描画確認: LibreOffice で PDF 化し、ページ画像を目視（または画像比較）する。LibreOffice は検証専用で、構造の正しさは読み戻しで担保する。
